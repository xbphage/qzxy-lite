# 04_蓝牙 BLE 协议与数据包示例

本文档基于 `趣智校园 v6.5.27` 真实脱壳 Dex 反编译代码（`com.klcxkj.bluesdk`、`libklcxkjencry.so`）以及现场抓包日志（`btsnoop_hci_261123_225033.log`）进行 100% 字节级还原，详细解释所有广播、GATT 与通信帧的**每一个字段含义**。

---

## 一、 高校脱机水表原理与架构

高校校园内大量安装的水表为**无蜂窝网络（脱机）水表**：
- 水表本体不具备 4G/NB-IoT 模块，无法与服务端维持 TCP 长连接；
- 若直接调用远程 TCP 下单接口（`/order/tcpDevice/downRate/rateOrder`），云端在探测设备无 TCP 链路后直接返回 `errorCode: 306`（“设备不在线”）；
- 必须由**手机 App 作为蓝牙中继网关**：
  $$\text{手机} \xrightarrow{\text{BLE}} \text{水表(读参数/随机数)} \xrightarrow{\text{HTTP}} \text{云端(签发开阀密文)} \xrightarrow{\text{BLE}} \text{水表(开阀)} \dots \xrightarrow{\text{BLE}} \text{水表(关阀/账单)} \xrightarrow{\text{HTTP}} \text{云端(扣费结算)}$$

## 二、 蓝牙广播数据包字段详解 (Advertisement Data)

智能水表待机时持续广播 BLE 报文，用于手机发现设备与换取云端元数据。

### 1. 广播数据包示例 (Raw Hex)
```text
02 01 06 0B 09 4B 4C 43 58 4B 4A 5F 32 30 31 0A FF 5B 01 00 01 C0 7F 0E 3E 59 C5
```

### 2. 广播数据包字段逐项拆解说明
| 字节范围 | 长度 | 字段名称 | 原始 Hex 值 | 字段含义与解析说明 |
| :--- | :---: | :--- | :--- | :--- |
| **0x00** | 1B | `Flags Length` | `02` | Flags 结构体长度（2 字节）。 |
| **0x01** | 1B | `Flags Type` | `01` | 广播数据类型：`0x01` 代表广播标志位 (Flags)。 |
| **0x02** | 1B | `Flags Value` | `06` | 位掩码 `0x06`：Bit 1 置 1 代表通用可发现模式 (LE General Discoverable)；Bit 2 置 1 代表不支持经典蓝牙 (BR/EDR Not Supported)。 |
| **0x03** | 1B | `Name Length` | `0B` | 广播设备名称段长度（11 字节）。 |
| **0x04** | 1B | `Name Type` | `09` | 广播数据类型：`0x09` 代表完整本地设备名 (Complete Local Name)。 |
| **0x05 - 0x0E** | 10B | `Local Name` | `4B 4C 43 58 4B 4A 5F 32 30 31` | ASCII 解码为 **`KLCXKJ_201`**。前缀 `KLCXKJ` 代表凯路创新科技，后置 `201` 代表该设备所属的高校项目 ID (ProjectId=201)。客户端依赖该前缀过滤水表。 |
| **0x0F** | 1B | `Mfr Length` | `0A` | 厂商自定义数据段长度（10 字节）。 |
| **0x10** | 1B | `Mfr Type` | `FF` | 广播数据类型：`0xFF` 代表厂商自定义数据 (Manufacturer Specific Data)。 |
| **0x11 - 0x12** | 2B | `Company ID` | `5B 01` | 蓝牙 SIG 厂商标识代码（低位在前，`0x015B`）。 |
| **0x13 - 0x14** | 2B | `Device Model` | `00 01` | 内部硬件设备型号与固件版本标识代码。 |
| **0x15 - 0x1A** | 6B | `Factory MAC` | `C0 7F 0E 3E 59 C5` | 出厂硬件识别物理 MAC 地址。注：以 `C0` 开头时需归一化替换为 `00`（即 `00:7F:0E:3E:59:C5`）或以 `C4` 开头上传。 |

## 四、 串口通信帧协议结构说明 (Over-The-Air Protocol)

水表工作于透传模式，每一包传输的数据包含**外层 ASCII 封装**与**内层二进制数据帧**。

```text
外层格式：# [内层二进制字节流的 Hex 字符串] \n
```

### 内层二进制通用帧结构
```text
+--------+---------------+-----------+--------+--------+-------------+----------+--------+
| 引导头 | 长度 (Total)  | 方向标志  | 命令字 | 子命令 | 载荷 Payload| 校验和   | 结束符 |
| 1 Byte | 2 Bytes (BE)  | 1 Byte    | 1 Byte | 1 Byte | N Bytes     | 1 Byte   | 1 Byte |
+--------+---------------+-----------+--------+--------+-------------+----------+--------+
|  0x60  | payload.len+3 | 0x80/0x81 |  Cmd   |  0x00  | Data...     | Checksum |  0x16  |
+--------+---------------+-----------+--------+--------+-------------+----------+--------+
```

#### 内层通用字段含义表
| 字段名称 | 字节长度 | 取值规则与含义 |
| :--- | :---: | :--- |
| **引导头 (Header)** | 1 字节 | 固定为 `0x60`（十进制 96），用于帧同步标识。 |
| **总长度 (Length)** | 2 字节 | 大端序（Big-Endian）。数值等于：`载荷长度 + 3`（包含方向、命令字、子命令）。 |
| **方向标志 (Direction)** | 1 字节 | `0x80`：主机发往从机（手机 $\rightarrow$ 水表）；<br/>`0x81`：从机发往主机（水表 $\rightarrow$ 手机）。 |
| **命令字 (Cmd)** | 1 字节 | 标识业务操作类型：`0x23`=查询设备；`0x21`=下发开阀；`0x22`=关阀；`0x85`=采集账单；`0x86`=确认存储。 |
| **子命令 (SubCmd)** | 1 字节 | 业务子操作标识/序列号，常规通信中固定为 `0x00`。 |
| **载荷数据 (Payload)** | N 字节 | 具体业务参数、密钥密文、设备信息或账单记录。当作为响应时，第 1 个字节固定为执行状态码（`0x80` 代表成功）。 |
| **校验和 (Checksum)** | 1 字节 | 累加校验和（取低 8 位）：`Checksum = (方向 + 命令字 + 子命令 + sum(Payload)) & 0xFF`。 |
| **结束符 (End)** | 1 字节 | 固定为 `0x16`（十进制 22），标志一帧完整结束。 |

## 六、 Native 签名机制与字段算法 (JNI Signature)

调用云端蓝牙下单接口 (`/order/downRate/bluetooth/rateOrder`) 与消费上传接口 (`/order/upload/bluetooth/data`) 时，必须携带 `signature` 参数，否则接口报错。

### 1. 签名参数字典与排序规则
- **开阀下单签名源字段**：`telephone`, `deviceId`, `xfModel`, `randomNumber`
- **消费上传签名源字段**：`loginCode`, `telephone`, `xfData`

签名必须按字段名的 ASCII 升序字典排序拼接为：
`Key1Value1Key2Value2...`

### 2. 真实签名计算实例 (libklcxkjencry.so 双重 MD5 逆向还原)
以开阀下单为例：
- `deviceId`: `"19931"`
- `randomNumber`: `"e1000000"`
- `telephone`: `"13800138000"`
- `xfModel`: `"0"`
- `loginCode`: `"ea62297dfa0cb58a19b47bbff6637c8b"`

#### 第一阶段：拼接 loginCode 计算第 1 次 MD5
1. 将参数按 Key ASCII 字典序排序拼接：
   `deviceId19931randomNumbere1000000telephone13800138000xfModel0`
2. 追加 `&key=` 与 `loginCode`：
   `deviceId19931randomNumbere1000000telephone13800138000xfModel0&key=ea62297dfa0cb58a19b47bbff6637c8b`
3. 计算 MD5 并转为 32 位小写 Hex：
   `hash1 = md5(str1)`

#### 第二阶段：追加全局密钥加盐计算第 2 次 MD5
1. 拼接全局密钥常量 `&key=sign-kailu-855c74a88b8b494187c99b08b8c9a744`：
   `str2 = hash1 + "&key=sign-kailu-855c74a88b8b494187c99b08b8c9a744"`
2. 计算 MD5 并转为 32 位小写 Hex：
   `signature = md5(str2)`

> [!NOTE]
> 官方 `libklcxkjencry.so` 中的 `checkSignature` 函数会校验当前应用包名是否为 `com.klcxkj.zqxy` 且签名证书 Hash 是否匹配。若在第三方客户端（如 `com.qzxy.lite`）中调用，原生方法会静默返回 `"error_signature"`。因此 Lite 客户端必须过滤 `"error_signature"` 并直接使用纯 Kotlin 实现的双重 MD5 计算最终签名。

## 七、 现场抓包流量与脱壳 DEX 取证审计说明 (HAR vs BTSnoop 对账)

为彻底查清现场抓包文件 `open.e.kuaishou.com_2026_11_23_22_51_28.har` 与 `btsnoop_hci_261123_225033.log` 的对应关系与数据差异，特进行跨抓包、跨反编译代码的严格字节级审计：

### 1. 抓包时间轴与关联关系
*   **蓝牙 HCI 抓包 (`btsnoop_hci_261123_225033.log`)**：记录了 `2026-11-23 22:50:33` 至 `22:50:41` 期间，手机 App 与物理水表进行的完整 BLE 交互（查询 $\rightarrow$ 开阀 $\rightarrow$ 出水 $\rightarrow$ 关阀 $\rightarrow$ 读账单 $\rightarrow$ 确认存储）。
*   **网络 HTTP 抓包 (`open.e.kuaishou.com_2026_11_23_22_51_28.har`)**：生成于 `2026-11-23 22:51:28`（即蓝牙洗浴操作结束约 1 分钟后），记录了抓包代理软件捕获的出站网络流量。

### 2. HAR 文件中水表业务接口缺失的根本原因
审计 HAR 文件中的全部 238 条记录：
1. **绝大多数为广告 SDK**：其中 231 条请求目的地为快手广告 (`open.e.kuaishou.com`)、穿山甲广告 (`pangolin-sdk-toutiao.com`)、腾讯优量汇、Sigmob 等广告聚合平台；
2. **仅 7 条涉及 `china-qzxy.cn` 域名**：
   - 序号 #69: `CONNECT https://app-cold-water.china-qzxy.cn:443`，响应状态为 `0 (aborted)`，连接被客户端底层强制拒绝中止；
   - 序号 #168、#201: 从 `oss.china-qzxy.cn` 获取图标静态图片 (HTTP 200)；
   - 序号 #193-#196: `CONNECT https://oss.china-qzxy.cn:443` 建立 TLS 隧道。
3. **关键发现：`app-cold-water.china-qzxy.cn` 的真实用途**：
   - 逆向脱壳 DEX (`source-9319059-172502f5.dex`) 全局检索，该域名仅在两个类中硬编码：
     - `com.klcxkj.zqxy.ui.device.apartment.bill.BillDetailH5Activity`：加载账单详情 H5 页面 (`/billDetail?orderNo=...`)；
     - `com.klcxkj.zqxy.ui.activity.ActivityDetailActivity`：加载优惠券/活动 H5 页面 (`/coupon?data=...`)。
   - **结论**：`app-cold-water.china-qzxy.cn` 根本不是水表计费下单的后端 REST API 网关，而是展示 H5 网页的 WebView 页面域！
4. **业务请求未被明文捕获的机理**：
   - Android 7.0+ 系统启用了严苛的 Network Security Config / SSL Pinning，官方 App 默认不信任用户自行安装的 Charles/Reqable/Fiddler 根证书；
   - 序号 #69 的 `CONNECT app-cold-water.china-qzxy.cn` 出现 `aborted` 即为证书未受信任导致的 TLS 握手失败；
   - 官方 App 中脱机蓝牙的核心接口（由 `BaseDeviceActivity` 调用 `uh.c`，指向 `https://wfwoff.china-qzxy.cn/offlineOrder/...`）以及主网关 `https://v3-api.china-qzxy.cn/` 因证书校验失败被客户端直接阻断或直接绕过了代理，因此没有留存明文请求体。

### 3. 数据表与代码的一致性修复汇总
1. **阀门状态字段纠偏**：纠正了将查询响应 `0x22-0x23` 误标为 `macType` 的错误，确认为 `0x22-0x23` 是阀门当前运行状态（`0000`=关闭断水，`0100`=开启出水）；
2. **随机数字段性质澄清**：澄清了 `0x1E-0x21`（`randomNumber`）底层来自水表 MCU 内部单调时钟秒数计数器，在出水 22 秒后准确递增 22（`0xE1` $\rightarrow$ `0xF7`）；
3. **代码已严格同步**：`BleFrameCodec.kt` 已更新 `parseQueryResponse`，正确解析 `isValveOpen` 并在 `macType` 上提供与官方 App 一致的 `0001` 兼容映射。
